# majority-agreement-llm-patches
Replication package for the study "Can Majority Agreement Indicate Correctness? Oracle-Free Assessment of LLM-Generated Patches for GitHub Issues"

# Replication Package

This repository contains the replication package for the paper:

**Can Majority Agreement Indicate Correctness? Oracle-Free Assessment of LLM-Generated Patches for GitHub Issues**

The replication package contains the experimental pipeline for the two benchmarks used in the study:

- `SWE-Bench-Verified/` — scripts for SWE-Bench-Verified
- `SWE-Bench-Pro/` — scripts for SWE-Bench-Pro

Each benchmark folder in the GitHub repository initially contains the `Scripts/` directory. The benchmark-specific `data/` directory is provided separately through Zenodo as `data.zip`because of its size.

# Downloading the Data: [ZENODO LINK]

Download `data.zip`. The archive contains the data required to reproduce the experimental pipeline for both benchmarks. For each benchmark, the corresponding `data/` directory contains five main folders:

```
data/
├── clustering_results/
├── llm_outputs/
├── predictions_from_replacements/
├── prompts/
└── swebench_csv_results/
```

These folders contain the intermediate and final artifacts produced throughout the study:
- clustering_results/ contains the similarity and clustering results used for the agreement analyses reported in the paper.
- llm_outputs/ contains the responses generated by each evaluated LLM for the benchmark issues across the 11 temperature settings.
- predictions_from_replacements/ contains the processed LLM responses after applying the generated replacement instructions, including the resulting candidate changes in diff format used in the testing stage.
- prompts/ contains the prompts constructed for the benchmark issues and provided to the LLMs.
- swebench_csv_results/ contains the results obtained by evaluating the generated candidate patches with the SWE-bench evaluation harness, stored as CSV files.

Move each  `data/` directory into the corresponding benchmark folder in this repository, next to `Scripts/`.

# 1. Building the Prompt from the Benchmark

This part of the replication package corresponds to the methodology described in:

- **Section 4.1 — Benchmarks**
- **Section 4.2 — Fault Localization**
  
This directory contains:

```
BuildPrompt_from_Benchmark/
├── download_swe.py
└── utilities.py
```

## `download_swe.py`

This script downloads the corresponding SWE-bench dataset and processes its benchmark instances.

For each issue, the script uses the benchmark-provided reference patch to extract the paths of the repository files modified by the reference solution. These reference file paths are  used to retrieve the relevant repository files that are provided to the LLM when generating candidate patches.

## `utilities.py`

This file contains utility functions used by the benchmark-processing and prompt-construction pipeline.




# 2. Prompting the Models

```
PromptingModels/
├── chatgpt_prompting.py
├── claudeprompting.py
└── TogetherAI_prompting.py
```

The prompting scripts contain the model- and provider-specific settings used in the study, including the model identifier, message-role configuration, and maximum output-token setting used when querying each model.

The three evaluated models are:

- **GPT-4.1 mini**, prompted using `chatgpt_prompting.py`.
- **Claude Haiku 4.5**, prompted using `claudeprompting.py`.
- **Qwen3-235B-A22B**, prompted through Together AI using `TogetherAI_prompting.py`.

For each GitHub issue, these scripts use the prompt constructed in the previous stage and query the corresponding model at 11 decoding temperatures, from 0.0 to 1.0 in increments of 0.1. 

The generated responses are saved as text files. Each response contains the replacement instructions proposed by the model, which are processed in the next stage to construct candidate patches.


# 3. Processing Replacements and Syntax Validation

This part of the replication package corresponds to **Section 4.4 — Processing LLM-Generated Replacements** of the paper.


This directory contains:

```
ProcessingReplacements/
├── make_patch_from_replacement.py
```

## `make_patch_from_replacement.py`

This script processes the replacement instructions generated by the LLMs and applies them to the corresponding repository files.

For each replacement instruction, the processing first searches for the specified code segment using exact matching. If an exact match is not found, an indentation-insensitive line-by-line search is used so that small indentation differences in the generated replacement instruction do not automatically prevent the intended code location from being identified. If the target code cannot be located, the generated response is treated as invalid and is not used in the subsequent analysis.
Syntax validation is selected according to the modified file's suffix/extension. The pipeline uses the corresponding language-specific syntax checker or parser for the file type. This includes `py_compile` for Python files, Node.js for JavaScript files, `tsc` for TypeScript files, and `gofmt` for Go files, together with parsers for configuration formats such as JSON, YAML, XML, and TOML.


# 4. Testing Candidate Patches

This part of the replication package corresponds to **Section 4.5 — Candidate Patch Construction and Testing** of the paper.


This directory contains:

```
Testing/
└── llm_fix_evaluation_swebench_parallel.py
```

The testing script evaluates the candidate patches using the corresponding SWE-bench evaluation procedure.

To make the evaluation more efficient, the benchmark is partitioned by repository into parallel shards. The number of shards is set to the number of repositories in the corresponding benchmark, so issues belonging to different repositories can be evaluated in parallel. The evaluation also uses cached repository and environment artifacts where possible to reduce repeated setup work and speed up execution.

For each candidate patch, the testing stage prepares the corresponding repository state, applies the patch, and runs the benchmark tests used to determine whether the issue has been resolved. The resulting pass/fail outcomes are then used as the correctness labels in the subsequent analysis.
